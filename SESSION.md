- 2026-08-26 23:05 — Fixed karaoke misalignment for real, verified by measurement (345cb5a). Diagnosis was done with an instrumented Playwright run (`/tmp/lg-e2e/watch3.mjs`) that intercepts caption poll responses and, every second, compares the DOM-highlighted word against the word the relay audio clock says should be lit. Before: 27% match, highlight ~8s ahead. Two root causes. (1) whisper.cpp word timings were fake — `t_dtw=-1`, times were linear interpolation across each segment ("Suscríbete" allegedly 3.8s). Fix: spawn whisper-server with `--dtw large.v3.turbo --no-flash-attn` (flash-attn silently disables DTW; config `whisperDtwPreset`, env `WHISPER_DTW_PRESET`), and `normalizeFlatWords` now prefers `t_dtw` (centiseconds, ≈token end; token spans [prev end, own t_dtw]) when ≥80% of entries carry it. Costs ~1.5s per 15s clip — acceptable. (2) The audio relay consumed its byte buffer destructively, so any second browser connection (preload probe, StrictMode double-mount) started mid-stream, breaking the currentTime↔session mapping. Relays now keep per-connection cursors (chunk `seq`) over the shared append-only buffer and always serve from the start; buffer is trimmed by age only (180s cap). With that guarantee, `audio.currentTime` IS the session clock — deleted `reanchorPlayback` and the anchor machinery entirely from `captionSync.ts`/`CaptionsPanel.tsx`; the wall-clock snap was the thing pushing the highlight ~8s (the buffering margin) ahead. After: 97% word-for-word match, median offset 0ms, p90 0ms, on a station playing song lyrics. Note: reconnects also resolve correctly now (relay replays from session 0), but a reconnect after the 180s buffer cap would misalign — accepted for v1. Verified: server 63 tests pass (3 new DTW tests, 1 new multi-connection relay test), frontend 19 pass, tsc clean both, live browser measurement above. Killed stale whisper-server processes so the app respawned with DTW flags.
